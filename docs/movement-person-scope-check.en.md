# Person-scoped movement queries: verification

[Español](movement-person-scope-check.es.md) · [Usage](usage.en.md)

Verified on 2026-10-08. Movement searches now distinguish the recording author, internal payer/recipient and an affected account's manager. The saved event supplies the requester identity; explicit member IDs must identify a known household member. Family/personal classification remains independent. Filtering occurs in SQL before ordering, display limits, counts and totals. An empty own result never falls back to household records.

Financial-date ordering and registration-time ordering are separate. Numeric IDs break ties, and JSON aggregation preserves that order. The default search remains household-wide for compatibility. Transfer and loan totals remain separate from income/expense totals; totals cover all matching records, not only the displayed page. The RPC is STABLE, SECURITY INVOKER and executable only by the backend service role.

Validation: the full implementation suite passed **452/452** with typecheck. Eleven new automated regressions cover own/global/named-person scopes, differing roles, old own records beyond 30 newer household records, ordering, exact amounts/dates/accounts, invalid inputs, reversals, read-only behavior, period totals and movement classification. Ten of the eleven new regressions failed before their respective fixes; the read-only/reversal check already passed. The public checkout and VPS each passed the 24 movement-search tests and typecheck.

A real-model evaluation passed **16/16** using a disposable synthetic PGlite ledger: the original wording, paraphrases, author versus recipient/manager, an empty result, named members, global/own follow-ups, a named-person correction, historical queries, period totals and ambiguity. See the [synthetic report](movement-person-scope-model-acceptance.json) and [reproducible evaluator](../scripts/movement-person-scope-eval.ts). The evaluator reads an existing protected owner token, does not refresh OAuth and makes no Telegram calls or production ledger writes. Its durations are agent-test timings, not end-to-end Telegram latency or a universal performance guarantee.

Deployment verification used read-only queries against the existing ledger and confirmed the intended own versus global records, unchanged ledger checksums, enabled manager approvals and no pending intake/deliveries. Startup/readiness and a consistent private offsite backup were checked. Deployment encountered missing linked runtime dependencies on restart; dependencies were restored and readiness verified before activating the accepted candidate. No account, balance or historical transaction was changed by this fix. Public verification data is synthetic; production identities, infrastructure and exports are excluded.
